# P3：跨进程并发安全与端到端压测

本轮补齐两个真实缺口：**多个进程写同一份 JSONL 历史会互相踩行**，以及**从未做过端到端连续压测**。

## 1. 跨进程文件锁

新增 `evolution/file_lock.py`：

- Windows 用 `msvcrt.locking` 的字节区间锁，POSIX 用 `fcntl.flock`，均为非阻塞尝试 + 轮询重试；
- 锁文件是目标文件同目录的 `<name>.lock` 侧车文件，含 1 个填充字节（Windows 字节锁要求文件非空）；
- `timeout=None` 表示一直等；超时抛 `FileLockTimeoutError`；进程退出后操作系统自动释放，残留锁文件不影响后续加锁。

接入位置：

| 位置 | 行为 |
| --- | --- |
| `EvolutionHistoryStore.append` | 线程锁 → 进程锁 → 追加一行 → `flush` + `os.fsync`（`flush_each_record` 时） |
| `EvolutionHistoryStore.load` | 进程锁内整文件读取，避免读到写了一半的行 |
| `AlphaEvolutionEngine.save_checkpoint` | 同路径并发写串行化，再走 `mkstemp` + `os.replace` 原子替换 |

配置：`EvolutionHistoryConfig.lock_timeout`（默认 10 秒）会随 checkpoint 的 `history_config` 一起持久化，恢复时沿用同一超时；锁超时统一转成 `EvolutionHistoryLockError`。

**能力边界（必须一起理解）**：

- 这是 advisory lock，只约束同样调用本模块的进程；外部脚本用 `>>` 直接追加不受保护。
- 保证的是「一次 append 一整行、原子可见」；读者拿到的是文件一致前缀，不做快照隔离。
- 网络文件系统（NFS/SMB）的锁语义因实现而异，跨机器共享同一 JSONL 不在保证范围内。

## 3. 端到端压测

新增 `scripts/stress_v310_e2e.py`，每次迭代包含两条链路：

1. **研究链路**：`V310ResearchPipeline.run()` 全流程（建任务 → 收集 3 份报告 → 交叉校验 → 辩论 → 共识 → 投委会 → 落盘 `decision.json`），断言决议为 `approved/approved_with_conditions`、`quorum_met=True`。
2. **进化链路**：跑 2 代 → checkpoint → `from_checkpoint` 续跑 2 代，与不中断跑 4 代比对代际和最佳 fitness。

实测结果（2026-11-16）：

```
python scripts/stress_v310_e2e.py --iterations 20
40/40 passed in 7.2s
```

即 20 次研究全链路 + 20 次断点续跑，全部一致通过。只跑研究链路（不装 numpy/pandas）可加 `--skip-evolution`。

CI 侧只保留 3 次快速压测 `tests/ai_team/test_stress_quick.py`（`--skip-evolution`，约 3.7s），避免给 workflow 引入 numpy/pandas。
